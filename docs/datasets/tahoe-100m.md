# Tahoe-100M dossier

A primary-source rundown of Tahoe-100M, written to drive v0 planning for the cellduet cross-modal study. The dossier establishes one project-level finding up front, because it changes the framing of the whole concordance question.

**Project-level correction.** Tahoe-100M is a **small-molecule (drug) perturbation atlas, not a CRISPR/sgRNA atlas.** The Hugging Face card and the bioRxiv abstract describe it as "100 million transcriptomic profiles from 50 cancer cell lines exposed to 1,100 small-molecule perturbations" ([HF dataset card](https://huggingface.co/datasets/tahoebio/Tahoe-100M), [bioRxiv 2025.02.20.639398](https://www.biorxiv.org/content/10.1101/2025.02.20.639398v1)). There is no sgRNA library, no CRISPRi/CRISPRa/KO arm, and no NTC sgRNA control. Vehicle controls are DMSO. RxRx3 by contrast is a CRISPR-KO morphology dataset. Direct gene-by-gene matching is therefore not what Tahoe-100M supports out of the box. The project must either (a) reframe v0 as agreement between *drug-target gene proxies* on the Tahoe side and CRISPR-KO genes on the Recursion side, restricted to the ~280 genes Tahoe drugs target, or (b) replace the Tahoe-100M arm with a genuinely CRISPR-perturbed transcriptomic dataset (e.g., Replogle K562/RPE1, the Arc Virtual Cell Challenge H1 hESC dataset, or the Replogle-Nadig set referenced by STATE). This decision belongs in the brainstorm, not in this dossier, but the dossier is written assuming Tahoe-100M stays in scope.

## Origin and citation

Tahoe-100M was generated by **Vevo Therapeutics** (also branded "Tahoe Therapeutics" / tahoebio) on their Mosaic high-throughput single-cell platform, and released open-source on **2025-02-25** as the inaugural contribution to the **Arc Institute Virtual Cell Atlas** ([Arc Institute press release](https://arcinstitute.org/news/arc-vevo)). The accompanying preprint is Zhang et al., *"Tahoe-100M: A Giga-Scale Single-Cell Perturbation Atlas for Context-Dependent Gene Function and Cellular Modeling,"* bioRxiv 2025.02.20.639398, DOI [10.1101/2025.02.20.639398](https://doi.org/10.1101/2025.02.20.639398). The current preprint version on bioRxiv is v3 (May 2025). I could not get a 200 OK from bioRxiv during research (403 on direct fetches), so version-specific deltas are unverified; treat that as an empirical check before citing v3-only numbers.

The dataset license on Hugging Face is **CC0-1.0** (public domain dedication, [HF metadata](https://huggingface.co/datasets/tahoebio/Tahoe-100M/blob/main/README.md)). Canonical landing pages: the [Hugging Face dataset](https://huggingface.co/datasets/tahoebio/Tahoe-100M), the [Arc Virtual Cell Atlas tools page](https://arcinstitute.org/tools/virtualcellatlas), and the [Arc-Institute/arc-virtual-cell-atlas GitHub](https://github.com/ArcInstitute/arc-virtual-cell-atlas/blob/main/tahoe-100M/README.md). No formal version string is published; the HF repo uses git revisions.

## Biological scope

**Perturbation type: small molecules, not CRISPR.** No sgRNA library. Vehicle control is `DMSO_TF`, paired plate-by-plate. Per the HF schema, controls are obtained by joining on the (`drug == "DMSO_TF"`, `plate`) tuple ([HF README](https://huggingface.co/datasets/tahoebio/Tahoe-100M/blob/main/README.md)).

**Drug count.** The `drug_metadata` parquet table has **379 unique drugs** (verified by downloading `metadata/drug_metadata.parquet` from the HF repo and counting rows). The widely repeated "1,100 small-molecule perturbations" figure refers to drug *conditions* (drug + concentration combinations), not unique compounds. Concentrations vary; the [Tahoe blog walkthrough](https://www.tahoebio.ai/news/walking-through-our-tahoe-100m-manuscript) describes "~400 compounds tested across 50 cancer models, each at three doses." The replicate/dose-resolved condition count is what gives 1,100; the chemical-distinct count is 379.

**Drug-target genes.** From the `targets` column of `drug_metadata`: **264 of 379 drugs carry a gene-target annotation**, covering **280 unique target gene symbols** (verified locally on the parquet). Targets were proposed by GPT-4o from compound names and validated against MedChemExpress, per the [HF README](https://huggingface.co/datasets/tahoebio/Tahoe-100M/blob/main/README.md), so they are usable as a coarse map but not authoritative. The 325-genes / 120-multi-targeted figure that circulates online is sourced from the manuscript text and likely reflects an earlier or differently-counted target list; my parquet count (280) is the ground truth for what users will load.

**Cell lines.** The dataset spans **50 cancer cell lines profiled together** in pooled "cell village" wells. After QC, **47 cell lines** are usable; three were dropped as low quality ([DNAnexus dataset page](https://academy.dnanexus.com/public-datasets-on-the-dnanexus-platform/tahoe-100m), [Tahoe blog](https://blog.tahoebio.ai/p/target-deconvolution-through-data)). The `cell_line_metadata.parquet` table I downloaded lists 102 unique `cell_name` rows because each cell line is repeated once per driver mutation; collapsing to unique names gives 102 names with driver annotations, of which 50 are the actually-perturbed lines (DepMap-traceable; e.g., A549 / ACH-000681 / CVCL_0023, MCF-7 / ACH-000019 / CVCL_0031, HCT116, PANC-1, NCI-H460). The full set spans 13 organs; the dominant tissues by line count are Lung, Bowel, Pancreas, and Skin. Most lines carry well-known oncogenic driver mutations: TP53 in 68 of the 102 metadata rows, KRAS in 52, CDKN2A in 38 (verified locally). The dataset is therefore **a cancer cell-line panel, not a tissue or primary-cell atlas**, and that bias affects every downstream gene phenotype.

**Cells.** The HF dataset card reports `num_examples: 95,624,334` after QC, against `100,648,790` total cells in the GitHub README. The expression table has ~95.6M cells, ~62,710 measured genes (Ensembl release 109, GRCh38), released as token-encoded count vectors plus a `gene_metadata` table mapping token IDs to symbols and Ensembl IDs ([HF dataset](https://huggingface.co/datasets/tahoebio/Tahoe-100M/blob/main/README.md), [Tahoe-100M-SCVI-v1 model card](https://huggingface.co/tahoebio/Tahoe-100M-SCVI-v1)).

**Replicate structure.** Every `(drug, concentration)` is delivered to a single sample (well), and `sample` is the unit that distinguishes biological replicates. There are **1,344 samples on 14 96-well plates** ([Arc GitHub README](https://github.com/ArcInstitute/arc-virtual-cell-atlas/blob/main/tahoe-100M/README.md)). Inside each well, the cell village contains all 50 lines simultaneously, demuxed from genotype using the `Cell_ID_Cellosaur` field. Per-line cell counts within a sample are not uniform; quality-metric columns (`mean_gene_count`, `mean_tscp_count`, `mean_pcnt_mito`) are tracked at sample level, not cell-line-within-sample level. Per-(drug, cell line) replication is therefore implicit, not designed: every drug is profiled once per cell line per dose in each plate it appears on, and replicate count per (drug, cell line) is small (typically 1 well unless the drug spans multiple plates).

## Disease-gene coverage

A precise answer requires distinguishing two questions: *is the gene measured?* and *is the gene perturbed?* Tahoe-100M perturbs with small molecules, so "perturbed" means "a drug in the dataset is annotated as targeting this gene." For a genuine gene-by-gene match against CRISPR-based morphology data, only the second question is the right denominator.

**All gene measurements verified by loading `gene_metadata.parquet` locally; perturbations verified against the `targets` column of `drug_metadata.parquet`.**

| Gene set | Measured (in 62,710-gene panel) | Drug-perturbed | Verdict |
|---|---|---|---|
| **Neurodegeneration core** (TARDBP, FUS, C9orf72, GRN, MAPT, SNCA, LRRK2, APP, PSEN1, PSEN2, SOD1, HTT, ATXN1/2/3, PARK7/DJ-1, PINK1, PRKN) | All 18 measured (PARK7 is the symbol; "DJ-1" is its alias and matches PARK7) | **0 drug targets** | **No.** Tahoe-100M has no useful coverage of any neurodegeneration gene as a perturbation target. Cell context is also wrong (cancer lines, no neurons). |
| **Oncology drivers** (TP53, KRAS, BRAF, EGFR, MYC, PIK3CA, PTEN, RB1, CDKN2A) | All 9 measured | KRAS 4 drugs (Adagrasib, BI-3406, Lonafarnib, RMC-6236), BRAF 4 (Dabrafenib, Encorafenib, Regorafenib, Vemurafenib), EGFR 12 (Afatinib, Erlotinib, Gefitinib, Almonertinib, etc.), MYC 2 (APTO-253, Arbutin), PIK3CA 4 (Alpelisib, Bimiralisib, GSK1059615, Torkinib). TP53, PTEN, RB1, CDKN2A: 0 drug targets (these are tumor suppressors, generally undruggable). | **Partial.** 5 of 9 covered as drug targets, 4 of 9 not, but the 5 that are covered are some of the most pharmacologically tractable oncogenes and have multi-drug evidence (especially EGFR with 12 distinct compounds), giving real signal. |
| **Cardiac** (MYH7, TTN, LMNA, KCNQ1, SCN5A) | All 5 measured | SCN5A 1 (Levobupivacaine, off-target). Others 0. | **No.** No cardiac biology is meaningfully perturbed. |

So Tahoe-100M is, for the cellduet question framed by gene targets, **a cancer-driver dataset**. Useful gene targets for v0 cluster around kinases (EGFR, ERBB2, FGFR1-4, MET, ALK, KIT, KDR, JAK1/2/3, BRAF, MAP2K1/2, PIK3CA-D, mTOR, CDK4/6, AKT1-3), nuclear hormone receptors (AR, ESR1, NR3C1, PGR, PPARA/G), epigenetic regulators (HDAC1-11, DNMT1/3A/3B), and a handful of metabolic / GPCR targets. Total drug-targeted gene universe: 280 symbols. None of those 280 are neurodegenerative or cardiac in the sense the brainstorm contemplates.

## Distribution and access

**Hosting.** Three primary mirrors, in ascending order of friction:
- **Hugging Face**, `tahoebio/Tahoe-100M`, parquet, **streamable** via `datasets.load_dataset(..., streaming=True)`. Total dataset size on HF: **`download_size: 337.6 GB`** ([HF README YAML](https://huggingface.co/datasets/tahoebio/Tahoe-100M/blob/main/README.md)). The DNAnexus mirror reports the unpacked size as **429 GB**. Auth: none, public.
- **Arc Virtual Cell Atlas, Google Cloud Storage**, current bucket `gs://arc-institute-virtual-cell-atlas` (Requester Pays after 2 TB/month free egress). Format: h5ad count matrices with `.h5ad.gz` internal compression, plus parquet metadata ([Arc GitHub README](https://github.com/ArcInstitute/arc-virtual-cell-atlas/blob/main/tahoe-100M/README.md)). The legacy bucket `gs://arc-ctc-tahoe100/` is deprecated as of 2026-03-31.
- **Google Cloud Marketplace BigQuery dataset**: `bigquery-public-data/arc-institute` ([listing](https://console.cloud.google.com/marketplace/product/bigquery-public-data/arc-institute)). Useful for SQL-style metadata queries without download.

**File formats.** Main expression table is parquet on HF (token-id encoded sparse rows: `genes: sequence<int64>`, `expressions: sequence<float32>`, plus per-cell metadata columns inline). On the Arc GCS bucket the same data is mirrored as h5ad. Metadata tables (`cell_line_metadata`, `drug_metadata`, `gene_metadata`, `sample_metadata`, `obs_metadata`) are small parquets a few MB to ~100 MB each and trivially fetchable.

**Pre-computed `pseudobulk_differential_expression`** is also distributed as a parquet config on HF; it has **4.09 billion rows** per the [DNAnexus listing](https://academy.dnanexus.com/public-datasets-on-the-dnanexus-platform/tahoe-100m). Size on disk is hundreds of GB; this is a per-(sample, gene) DE table, not a per-(drug, cell-line, gene) summary, but it is the closest thing to a turnkey pseudobulk product the project can use.

**Streaming on Colab Free.** Streaming via `datasets` works (Tahoe ships an [official loading tutorial](https://huggingface.co/datasets/tahoebio/Tahoe-100M/blob/main/tutorials/loading_data.ipynb) explicitly designed for the Colab pattern). The community [theislab/vevo_Tahoe_100m_analysis](https://github.com/theislab/vevo_Tahoe_100m_analysis/tree/tahoe-DGX-fix) tutorial is built around rapids-single-cell + dask on a DGX, which is not applicable to T4. The 337 GB raw size means downloading the full expression table to Drive is out of the question; streaming + filtering, or working from the `pseudobulk_differential_expression` table, is the only path.

## Pre-computed artifacts

This is the section that determines whether v0 is feasible without retraining anything.

**Tahoe-100M-SCVI-v1.** The most directly useful artifact. Released by Vevo on Hugging Face at [`tahoebio/Tahoe-100M-SCVI-v1`](https://huggingface.co/tahoebio/Tahoe-100M-SCVI-v1). It is an **scvi-tools** VAE: 1 layer, 128 hidden units, **10 latent dimensions**, 40,390,510 parameters, **MIT license**. The released minified AnnData object contains **per-cell embeddings for all 95,624,334 cells × 62,710 genes**, with `X_latent_qzm` (latent mean) and `X_latent_qzv` (latent variance) in `adata.obsm`. Storage requirement: **41 GB on disk and 41 GB RAM** to load the minified AnnData; model itself uses ~1 GB GPU memory ([model card](https://huggingface.co/tahoebio/Tahoe-100M-SCVI-v1)). Plate 14 was held out from training. **The 41 GB RAM requirement breaks Colab Free** (12 GB ceiling); the file also blows past the 15 GB Drive quota. This artifact is unusable in-session on Colab Free unless we fetch only a subset (one cell line, one drug class) by streaming the parquet `obs_metadata` first to filter cell IDs, then pulling the AnnData partition lazily.

**Tahoe-x1.** Released October 2025 by Tahoe ([`tahoebio/Tahoe-x1`](https://huggingface.co/tahoebio/Tahoe-x1), [bioRxiv 2025.10.23.683759](https://www.biorxiv.org/content/10.1101/2025.10.23.683759v1)). Three sizes: **Tx1-70M, Tx1-1B (~1.3 B), Tx1-3B**. Transformer encoder, MLM-pretrained on 266M cells (CellxGene + scBaseCamp + Tahoe-100M). **Apache-2.0** for both code and weights. Model produces per-cell embeddings (in `adata.obsm`) and optionally per-cell-context gene embeddings (in `adata.varm`). Embedding dimensionality is not stated on the HF card; the [tahoe-x1 GitHub](https://github.com/tahoebio/tahoe-x1) is the source of truth for that and for VRAM budgets. Public guidance is silent on T4 compatibility, but a 70M-parameter encoder in fp16 should sit well under 15 GB VRAM at modest batch sizes; the 1B and 3B variants will not fit T4 inference without aggressive quantization or CPU offload. **Importantly, Tahoe-x1 does not currently ship pre-computed Tahoe-100M cell embeddings as a downloadable artifact.** A user must run inference. For 95.6M cells on a single T4 this is not tractable in a 12-hour session. Empirical: estimate per-cell throughput on a Colab T4 with batch 128 to confirm. Even at 5,000 cells/sec (optimistic for a 70M transformer), 95.6M cells = ~5.3 hours, plus I/O. Realistic for a subset, infeasible for whole atlas in one session.

**STATE (Arc Institute).** The State Embedding (SE) and State Transition (ST) families ([`ArcInstitute/state` GitHub](https://github.com/ArcInstitute/state), [bioRxiv 2025.06.26.661135](https://www.biorxiv.org/content/10.1101/2025.06.26.661135v1)). The published SE checkpoint is **SE-600M** (~600M parameters), filename `se600m_epoch15.ckpt`, with weights gated under the **Arc Research Institute State Model Non-Commercial License** (CC BY-NC-SA-4.0 on code, separate non-commercial AUP on weights). For Tahoe-100M specifically, Arc ships a **trained ST model with a Colab tutorial for inference** ([Colab](https://colab.research.google.com/drive/1bq5v7hixnM-tZHwNdgPiuuDo6kuiwLKJ)), which strongly implies T4-tier compatibility for inference but not for training. Embedding dimensionality is not published on the README; pull from the checkpoint config. STATE-SE on the Tahoe data is the most plausible source of "free" per-cell embeddings, but the **non-commercial license** is a real constraint for any portfolio piece intended for downstream use; CC0-licensed Tahoe-100M counts plus an Apache-2.0 Tahoe-x1 inference run is the cleanest license stack.

**TranscriptFormer (CZI).** Trained on cross-species data, **not on Tahoe-100M** ([CZI announcement](https://chanzuckerberg.com/blog/transcriptformer-model-overview/), [Virtual Cells Platform listing](https://virtualcellmodels.cziscience.com/model/01966441-339f-77f7-aa06-f67636f865dc)). Not in scope for this dossier.

**The single tractable Colab-Free path** for v0 is: stream the `pseudobulk_differential_expression` parquet from HF, filter to (sample, gene) rows, aggregate to (drug, cell_line, gene) log-fold-change vectors, and use those LFC vectors as the per-(drug, cell_line) phenotype. Per-gene phenotypes (in the drug-target sense) come from rolling up drugs by their `targets` annotation. No model inference required. The whole pipeline lives in pandas / pyarrow / numpy and fits in <12 GB RAM if processed in chunks.

## Compute footprint for v0

The Colab Free tier is the binding constraint: **~12 GB RAM, 15 GB persistent Drive, T4 with ~15 GB VRAM, 12-hour session, ~90-min idle disconnect** (per the project brief).

**What does *not* fit.**
- Whole expression matrix (95.6M × 62,710, sparse): the parquet `download_size` is 337 GB. Cannot land on Drive.
- Tahoe-100M-SCVI minified AnnData: 41 GB Drive + 41 GB RAM. Hard no.
- Tahoe-x1 inference over the full atlas: bounded by 12-hour wall and tens-of-GB intermediate storage.

**What fits.**
- All metadata parquets (`cell_line_metadata` 19 KB, `drug_metadata` 40 KB, `gene_metadata` 1.3 MB, `sample_metadata` ~MB, `obs_metadata` ~hundreds of MB to a few GB; small enough to download fully).
- Streaming reads of expression data with on-the-fly aggregation. The HF `IterableDataset` keeps memory bounded.
- The `pseudobulk_differential_expression` table, **read in chunks** (4.09 billion rows; full table is many GB but per-(sample, drug) slices are tiny).
- A subset of pre-computed SCVI 10-d embeddings restricted to one cell line or one drug class. 1.5M cells × 10 floats = 60 MB. Trivial.

**Recommended aggregation strategy for v0.**

1. Fetch all five small metadata parquets to Drive (<10 MB total).
2. Download `pseudobulk_differential_expression` from HF in shards (config `pseudobulk_differential_expression`, sharded `train-*` files), filter to non-DMSO drugs, retain only `(sample, gene_symbol, log_fold_change)` columns. Join `sample` → `(drug, cell_line, plate)` via `sample_metadata` + `obs_metadata`.
3. For each `(drug, cell_line)` pair, materialize a length-62,710 LFC vector (or top-N HVG slice, e.g., 2,000 HVGs as STATE recommends). Stack into a small dense tensor: 379 drugs × ~50 cell lines × 2,000 HVGs × float32 = **~150 MB**. Easily in RAM.
4. To get a **per-gene transcriptomic phenotype** vector compatible with the morphology side, roll up: for each annotated drug target gene `g`, average the per-(drug-targeting-`g`, cell-line) LFC vectors across drugs and across cell lines. Output: 280 genes × 2,000 HVGs. ~2 MB. Trivially fits.
5. Per-gene-pair distance matrix: 280 × 280 cosine. Microseconds.

This avoids retraining, avoids any model inference, and stays inside the CC0 license boundary. The dimensionality decision (HVG count, whether to use SCVI 10-d in addition or instead) is empirical, see Open Questions.

## Known caveats

- **Cancer-cell-line confound.** The whole panel is cancer cell lines from 13 organs (lung 27, bowel 25, pancreas 11, skin 10, breast 7, etc., from local count of `cell_line_metadata`). Drug responses reflect cancer biology with constitutively active oncogenic drivers, not normal physiology. A "MYC drug effect" measured here is "MYC drug effect in TP53-null/KRAS-mutant cancer cells," not a generalizable MYC perturbation phenotype. This is the single biggest caveat for cross-modal comparison.
- **Cell-line heterogeneity demands per-(drug, cell-line) modeling, not pooled.** Vevo's own marketing line is that the cell village "eliminates batch effects" ([Tahoe blog](https://www.tahoebio.ai/news/walking-through-our-tahoe-100m-manuscript)), but the same blog frames the science as measuring "how various cell lines, with varying baseline genetics and gene expression, respond to various treatments." The biology is explicitly heterogeneous. Drug effects are context-dependent (this is the paper's thesis), so a single per-gene aggregate vector that pools all 47 lines will mask real signal. Per-(gene, cell-line) aggregates are the honest unit; whether to then average across lines for cross-modal comparison is a modeling choice, and a defensible v0 answer is to compute both and report both.
- **Plate effects.** Each plate contributes 96 wells × 50 cell lines = 4,800 cell groups. Plate 14 is the SCVI hold-out. Plate-matched DMSO controls are mandatory; the HF README is explicit about pairing on (`drug == 'DMSO_TF'`, `plate`). Failing to plate-match controls will produce spurious DE.
- **Pseudobulk DE table provenance.** The `pseudobulk_differential_expression` rows are pre-computed by Vevo. The exact statistical method (Wilcoxon? edgeR? DESeq2 on pseudobulks? pyDESeq?) is not in the README schema; the [paper](https://doi.org/10.1101/2025.02.20.639398) is the source of truth and the v0 notebook should pin the method down before trusting the LFCs. Empirical.
- **GPT-4o-derived target annotations.** The `drug_metadata.targets` column was generated by GPT-4o, then validated against MedChemExpress. Errors are possible. For any individual gene-of-interest claim, cross-check against a primary pharmacology database (DrugBank, ChEMBL).
- **Drug count ambiguity.** 379 unique drugs vs. 1,100 (drug, dose) conditions vs. 1,344 samples. Three different denominators in three different blog posts; pick one and stay consistent. The dossier uses 379 unique drugs as the canonical compound count.
- **Replicate count is shallow.** With 1,344 samples, ~3 doses per drug, 47 cell lines mixed in every well, each (drug, dose, cell_line) cell is represented in only one well per plate. Statistical power per (drug, cell_line) is bounded by the number of demuxed cells, which varies; this is a notebook-01 thing to characterize before trusting any individual phenotype vector.
- **License heterogeneity in the artifact stack.** Dataset is CC0; SCVI model is MIT; Tahoe-x1 is Apache-2.0; STATE weights are non-commercial. A cellduet portfolio piece that wants permissive distribution should stay on the CC0-and-Apache side and avoid STATE in the public pipeline.

## Open questions

These are the things that cannot be answered without actually loading data on Colab. Notebook 01 should resolve them in this order.

1. **Resolve the framing.** Is v0 "drug-target gene proxies vs CRISPR-KO morphology" (keeps Tahoe-100M, restricts to ~280 genes), or "swap Tahoe-100M for Replogle/Virtual Cell Challenge" (true CRISPR-vs-CRISPR comparison)? This is a brainstorm decision, not an empirical one, but it must come first. Everything below assumes the first option.
2. **What statistical method generated `pseudobulk_differential_expression`, and is plate-matched DMSO already accounted for?** Read the paper plus the table schema. If not plate-matched, recompute LFCs from raw counts via plate-paired comparisons.
3. **How many demuxed cells exist per (drug, dose, cell_line)?** Group `obs_metadata` by `(drug, drugname_drugconc, cell_line_id)` and report a histogram. Anything below ~50 cells per group is too noisy for reliable LFC.
4. **HVG selection.** Use Tahoe's recommended 2,000 HVGs (STATE's default) or compute project-specific HVGs across the 47 lines? Empirical.
5. **Per-gene phenotype: pool across cell lines vs. keep cell-line-stratified.** Compute both; correlate them. If correlations are high (cell-line-invariant signal), pool. If low, the project must report stratified results, which complicates the cross-modal comparison.
6. **SCVI 10-d as an alternative phenotype.** The 10-d SCVI latent is too compressed for direct gene-phenotype use, but per-(drug, cell_line) means in 10-d are tiny and trivial to store. Worth benchmarking against the LFC version as a sanity check, even if 41 GB AnnData is unloadable, because per-cell `obsm` slices can be fetched in chunks.
7. **Tahoe-x1-70M inference throughput on Colab T4.** If a subset (say, 1M cells from 5 cell lines under 50 drugs) can be embedded in <2 hours, it becomes feasible to run model-derived per-cell embeddings instead of hand-rolled LFC vectors and to compare the two approaches. Empirical.
8. **Gene symbol harmonization with the morphology side.** Tahoe uses HGNC + Ensembl release 109 + GRCh38. The Recursion side uses its own gene mapping. Confirm the join key with the other agent before writing any cross-modal code.
